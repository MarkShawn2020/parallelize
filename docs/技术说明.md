# JIS · Jev in the Shell · 技术说明

EvoTavern 4th · SECTION 9 多 Agent 蜂群协作 · 单人参赛：手工川
代码：https://github.com/lovstudio/jis （Apache-2.0）

---

## 一句话

一个没有指挥官的 Agent 蜂群：能写成规则的协调用规则，一个 token 不花；规则写不出来的判断交给 Jev 这样的判断模型；Jev 拿不准才请大模型，大模型的裁决经复核确认后变成判例，喂回给 Jev。

名字取自《攻壳机动队》：Ghost in the Shell 问的是壳里那个做判断的是什么，JIS 是 Jev in the Shell——蜂群是壳，Jev 是壳里做协调判断的那一层。塔奇克马把各自的经验同步给彼此，那个动作叫並列化，正是这里的知识继承层。

## 为什么做

多 Agent 协作有三个老问题：

1. **信息在汇总里丢。** EvoMap 自己的实验里，Sub-Agent 模式把 373 个做对的中间答案汇总之后只剩 207 个。
2. **协调贵。** 让大模型来协调，每条线索、每个“要不要复核”都要它想一遍，协调开销常常超过干活本身。
3. **会自我欺骗。** 几个 Agent 互相引用形成的“一致”，看起来像共识，其实只有一个信息源。

EvoMap 的赛题要求把一个点子交给 Agent 小队研究：结果要经另一位 Agent 复核才能继续；卡住时去 EvoMap 找别人试过的办法；跑通的经验留给后来者；在成员失效后接力完成；最后对比单 Agent 与蜂群在质量、速度、成本上的取舍。JIS 逐条对应这些要求。

## 怎么做

```
                 ┌──────────── 黑板（board 服务）────────────┐
 能力卡注册表 ──▶│ 原子认领 · 租约 · 按题号确定性合并 · 验收 │◀── 经验库 / EvoMap
                 └───────────────▲───────────────────────────┘
                                 │ 受限句柄（只能以自己的身份操作）
        ┌────────┬────────┬──────┴─┬────────┬────────┐
        │ cell 1 │ cell 2 │ cell 3 │  ...   │ cell N │   每个 cell：自己的模型、Gene 池、信誉
        └────────┴────────┴────────┴────────┴────────┘
             │ 规则写不出来的判断：要不要复核 / 收不收 Gene / 分歧谁对
             ▼
      System 1：Jev（带把握的选项）──把握不够──▶ System 2：大模型 ──复核确认──▶ 判例
```

**三层协调。** 认领、合并、租约这类能写成规则的，全部用规则，零 token。三类判断交给判断层：一个答案要不要让另一个 Agent 独立重做；邻居传来的 Gene 收不收；两个答案冲突时谁对。Jev 只输出选项和概率，只收输入 token；把握低于阈值才升级给大模型。

**协议。** Agent 之间只说一套类型化消息（ANNOUNCE、CLAIM、PROPOSE、REVIEW_REQUEST、ACCEPT、ECHO_ALARM、GENE_OFFER、LIBRARY_QUERY、QUARANTINE、DENIED 等）。每条消息带来源血统，传递的是限长摘要而不是完整对话。能力卡用于互相发现：谁擅长什么、信誉多少。完整规范见仓库里的 PROTOCOL.md。

**防虚假共识。** 每个答案都记录它“看过”哪些别人的答案。验收时数的是独立来源数，不是投票人数；一致但只有一个来源时触发回声警报，任务退回黑板，只有没接触过的 Agent 能接。

**容错与安全。**

- 成员失效：拔掉一个 Agent，它的租约到期后任务自动回到黑板，由别人接力。
- 信任边界：每个 Agent 只拿到绑定自己身份的受限句柄，不能替别人提交，也不能验收自己；越权操作会被拒绝并记录。
- 复核策略：新成员试用期内的答案全部复核；信誉低的必复核；其余随机抽检。
- 隔离：信誉按“答案是否与最终验收一致”更新，低于阈值自动隔离。
- 恶意成员：演示中可以一键“入侵”某个 Agent，让它专发错答案和有毒 Gene，观察系统如何识别并隔离它。
- 降级：一键让 Jev 离线，全部判断自动改由大模型完成；大模型也失败时，退回保守默认（必须复核、不收 Gene）。
- 校准守卫：某类判断上 Jev 与大模型分歧过大时，那一类直接交给大模型。

**知识继承。**

- Gene：复核通过的经验才会打包成 Gene 传给邻居；收不收由对方判断，没用的被遗忘。对应 EvoMap 的 gossip、adopt、forget 三条规则。
- 判例：大模型的裁决要等结果确认后才写回 Jev。
- 经验库：本地持久化，下一轮运行可以继承。
- EvoMap：任务卡住（连续复核不过）时，通过 EvoMap A2A 公开接口检索别人发布过的 Gene，外来 Gene 按不可信内容处理。运行结束后，只有在新题上通过留出集 A/B 验证门的 Gene，才按 GEP 打包成 Gene + Capsule + EvolutionEvent 发布回 EvoMap。

**两个场景，一套协议。**

- 数学与逻辑多步题：有标准答案，用于可证伪的对比实验。
- 点子验证：一个点子由大模型拆成若干可检验的论断，蜂群给出支持、反驳或不确定。其中混入已知真假的“金丝雀”论断，用来检验蜂群会不会被骗。最后按确定性规则给出继续、放弃或不确定的建议。

## 实验设计与结果

2026-09-23 真实运行：96 道困难合成题（6-9 步依赖运算、含干扰信息与单位换算，每题一个整数标准答案），做题模型统一为 Claude Haiku 4.5（与 EvoMap 实验同款），判断层 Jev（typesafe/jev-1.13），均经 OpenRouter；8 个 cell。原始记录在仓库 `runs/` 的对比文件与每次运行的 events / ledger / summary。

| 组织方式 | 准确率 | 总 token | 协调占比 | 成本（美元） | 耗时（秒） |
|---|---|---|---|---|---|
| 单上下文（96 题塞进一个上下文） | 63.5%（61） | 23.7k | 0 | 0.062 | 59 |
| 仅并行（每题各做各的 = 个体之和） | 80.2%（77） | 37.7k | 0 | 0.115 | 31 |
| Sub-Agent（协调者有损合并） | 80.2%（77） | 91.2k | 40% | 0.240 | 49 |
| 规则蜂群（无判断者） | 84.4%（81） | 52.5k | 8% | 0.154 | 44 |
| 大模型协调蜂群 | 83.3%（80） | 136.5k | 51% | 0.310 | 101 |
| **Jev 协调蜂群** | **88.5%（85）** | 169.2k | 57% | 0.296 | 102 |
| 同预算投票（与 Jev 蜂群同 token，每题多次独立作答取多数） | 90.6%（87） | 156.0k | 0 | 0.485 | 125 |

按题配对的精确 McNemar 检验（Jev 协调蜂群对比）：单上下文 31 比 7，p<0.001；个体之和 12 比 4，p=0.077；大模型协调 11 比 6，p=0.33；规则蜂群 9 比 5，p=0.42；同预算投票 7 比 9，p=0.80。

涌现复测：另取 192 道新题（种子 21），Jev 协调蜂群 92.7%（178），个体之和 83.9%（161），配对检验 22 比 5，p=0.0015。与主对照合并 288 题：91.3% 对 82.6%，34 比 9，p=0.00017。

读法：

- 协作的收益：同一个模型，“各做各的”80%，加上复核、分歧裁决和经验传递后 89%；复测与合并检验显著。一个上下文硬做只有 64%。
- 判断层：Jev 做了 104 次判断，共 0.002 美元，中位 0.47 秒；大模型判断从“大模型协调”的 155 次降到 77 次（单次中位 1.27 秒）。相同花费下，Jev 蜂群比大模型协调蜂群高 5 个百分点（差距尚不显著）。
- 同预算投票：准确率与 Jev 蜂群打平（差 2 题，不显著），但多花 64% 的钱、慢 22%；它的 token 全是大模型输出，蜂群的协调 token 大多是 Jev 的廉价输入。投票也没有接力、防作恶和经验继承。
- 校准守卫：本场 Jev 在“要不要复核”上与 Haiku 的判断 88% 不一致，守卫在 8 个样本后把这一类整体交还给大模型；“收不收经验”Jev 独立判定 67/73 次。Jev 独自放行“不必复核”的答案，本场错误率为 0。
- 相关错误：有 2 个以上独立来源仍然错的答案占 8.9%，这是同一底模带来的、来源追踪抓不到的错误。

继承实验：第一轮沉淀 12 条 Gene、17 条判例，第二轮换一批新题继承。继承后“收不收经验”的判断从 65 次降到 19 次。同题对照（同一批 64 题）：不继承 84.4%，继承 81.3%，差 2 题、不显著；协调 token 少约 19%，成本相近。结论：继承减少了重复判断，但本次没有提升准确率。

EvoMap 发布（真实）：一次 64 题运行结束后，2 条候选 Gene 在 8 道新题上做用与不用的 A/B。一条 7/8 对 7/8 未通过；一条 8/8 对 7/8 通过，已由认领节点 node_94cb40759974c569 发布为 Gene + Capsule + EvolutionEvent：<https://evomap.ai/asset/sha256:f09e2dd70fd8ad55c1110922f679c80bd59b08ae7f4f26b273746354888e333c> 。8 题多对 1 题只是很弱的正向信号，门槛如实写在 Capsule 内容里。

Jev 校准（离线，48 道真实困难题）：Jev 判断“这个答案要不要复核”的区分度 AUC 0.67。据此真实运行的升级门槛设为 0.2、复核门槛 0.4。

指标定义：

- 正确/千 Token：每千 token 做对的题数（不叫 AIR：EvoMap 的 AIR 是 能力 ÷ (Token × 时间 × 成本)，定义不同）。
- 协调占比：非解题 token 占总 token 的比例。
- 放行错误率：Jev 判为“不必复核”且没有升级的答案中，事后按标准答案核对为错的比例。
- 错了还被复核放过：有 2 个以上独立来源却仍然错的答案占比。

## 局限

- Jev 在难判断上的校准并不稳定，所以放行错误率和校准守卫会同时显示在屏上，不单看升级率。
- 所有 Agent 用同一个底模时会各自犯同一个错，来源追踪抓不到这类错误。“错了还被复核放过”这一列量化了它；复核改用不同家族的模型是下一步。
- 数学题由程序生成，便于得到标准答案；换成 GSM8K 只需换题库。
- 点子验证的结论来自模型已有知识，不是联网检索。
- 离线模拟模式只用于断网兜底，界面会明确标注 SIMULATION。
